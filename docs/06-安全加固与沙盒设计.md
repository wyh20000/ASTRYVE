# 安全加固与 Renderer Sandbox 设计

## 本轮已处理

- 模型流式输出在界面保持实时，但持久化按约 200ms 合并，结束、失败或停止时强制落盘。
- 本地 JSON 使用同目录临时文件后 rename，避免进程中断留下半个 JSON 文件。
- 模型请求增加连接超时、总响应超时、停止生成、按会话任务表，以及删除会话、关闭窗口、退出应用时取消。
- API Key 不再返回 renderer；旧明文配置启动时迁移到 Electron `safeStorage` 加密文件。系统加密不可用时只保留在内存。
- IPC 增加来源检查和消息、附件、模型 URL、模型配置等运行时校验。
- 外部链接仅允许 `https:`，阻止主窗口导航，默认拒绝网页权限，并启用 CSP。
- SSE 统一解析，支持 `\r\n`、多行 data 与无末尾换行的最后事件。
- 上下文同时受消息条数和近似 token 预算约束；图片能力改为模型预设的显式能力字段。
- MySQL 数据库名严格校验并转义，迁移仅忽略“字段已存在”错误。

## 为什么本轮不启用 `sandbox: true`

Electron 的 renderer sandbox 会让渲染进程运行在 Chromium 的受限环境中。它不能直接使用 Node.js、文件系统、子进程或任意原生模块。当前应用虽然已经使用 `contextIsolation: true` 和 `nodeIntegration: false`，但 preload 仍运行在非沙盒上下文；立刻切换可能影响现有 preload 打包、附件处理或未来 coding 功能尚未确定的接口。

`sandbox: false` 并不意味着 coding 能力必须放在 renderer。正确的长期结构是：

1. renderer 只负责界面、编辑状态和展示，不接触文件系统、终端、Git 凭据或 API Key；
2. preload 只暴露窄、可校验的业务 API，不能暴露通用 `invoke(channel, ...args)`；
3. 工作区读写、Git 和终端由主进程或独立 `utilityProcess` 执行；
4. 每次操作携带工作区 ID 和相对路径，主进程解析真实路径并确认仍位于授权根目录内；
5. 命令执行采用结构化参数和白名单能力，不把 renderer 字符串直接交给 shell；
6. 长任务有任务 ID、取消、超时、输出限速和窗口/项目生命周期；
7. 插件、代码分析器和不可信文档解析优先放入权限更低、可终止的独立进程。

完成上述边界后，再启用 `sandbox: true`，主要改动应集中在 preload 和少量 Electron 配置，而不会重做 coding 业务逻辑。

## 后续启用沙盒的验收条件

- preload 在 sandbox 模式可正常构建和加载；
- renderer 代码中没有 Node 全局、文件系统或子进程依赖；
- 所有工作区操作都有运行时校验、授权根目录检查和审计日志；
- 终端与工具调用可按任务取消，窗口销毁后不会继续向 renderer 推送；
- API Key、数据库密码和 Git 凭据不进入 renderer；
- 开启 `sandbox: true` 后通过发送消息、附件、模型切换、主题、coding 工作区和打包回归测试。
