# M16 桌面安全配对协议

## 范围

本文固定 AIAGENT 桌面端与独立 `ASTRYVE-chrome_develop_tools` 扩展的 M16-B 协议。
本阶段只建立受认证本地会话，不读取标签页，不注册浏览器工具，也不改变现有
`BrowserGateway` 的模型与普通插件边界。

## 固定身份与传输

- Native Host：`com.astryve.browser`。
- 扩展 ID：`lcjaalloempdgnhjjcpnckiniccpnacm`。
- 唯一允许来源：`chrome-extension://lcjaalloempdgnhjjcpnckiniccpnacm/`。
- 协议版本：`1`；内部单消息上限：200 KiB。
- 使用 Chrome Native Messaging 的本机 4 字节长度前缀和 UTF-8 JSON。
- Host 标准输出只写协议帧，诊断只写标准错误。

桌面程序由 `src/main/bootstrap.ts` 分流。普通启动继续进入原有 `index.ts`；只有精确
扩展来源参数进入 Native Host，其他扩展来源直接拒绝。

## 首次配对

1. 扩展生成 P-256 临时密钥和随机 client nonce，发送 `pairing.begin`。
2. Host 生成 P-256 临时密钥、host nonce、pairing ID 和两分钟挑战。
3. 双方对完整握手 transcript 使用 ECDH + HKDF 派生 256 位配对密钥。
4. 双方从配对密钥独立推导同一个六位码；扩展会拒绝不匹配的 Host 码。
5. 浏览器用户发送 HMAC 确认，桌面用户在 Electron 对话框中独立确认。
6. 只有两个确认都有效且未过期，Host 才通过 `safeStorage` 保存密钥并返回 HMAC 证明。
7. 扩展验证 Host 证明后，将密钥写入只允许可信扩展上下文访问的本地存储。

重新配对使用新的临时密钥并原子替换旧凭据；取消挑战不会替换旧配对。

## 重连与撤销

重连时双方交换新的 client/host nonce。Host 先用长期配对密钥证明身份，再用 HKDF
派生 15 分钟会话密钥；扩展和 Host 分别发送 `client-ready` 与 `host-ready` HMAC。

撤销消息绑定 pairing ID、session ID、request ID 和单调序号。Host 验证 HMAC 并删除
桌面密钥后返回认证的 `pairing.revoked` 回执；扩展随后删除本地凭据。离线清除仍会删除
扩展本地凭据，后续重新配对会原子替换桌面遗留项。

## 存储与进程边界

- 扩展先调用 `storage.local.setAccessLevel(TRUSTED_CONTEXTS)`，网页和内容脚本不能读取密钥。
- 桌面密钥只以 Electron `safeStorage` 密文原子落盘，拒绝不可用或 Linux `basic_text` 后端。
- Renderer、模型、普通插件和 Browser Gateway 不接收 Native Port、长期密钥或会话密钥。
- challenge 和 session 到期后从内存清理；消息 schema、版本、ID、大小和状态转换均精确校验。

## 安装与验收

`build/native-messaging/com.astryve.browser.json` 是 Host manifest 模板；
`scripts/register-chrome-native-host.ps1` 负责 Windows HKCU 注册和卸载。脚本不在开发或
构建时自动执行。自动化测试不能替代打包应用与真实 Chrome 的双端确认、重连、撤销、
伪造来源、错误证明和重放人工验收。

Chrome 边界的逐条官方规范映射记录在独立扩展仓库
`docs/architecture/chrome-developer-compliance.md`。Chrome Host 行为、manifest、参数、
帧格式、消息上限、stdout/stderr 和 Windows 注册方式均以 Chrome for Developers 的
[Native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)
文档为准，项目安全协议只能在其上增加限制，不能替代或放宽官方要求。
