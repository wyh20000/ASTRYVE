# 01 · 开发边界与规范

> 项目：**AI Agent**（类 Codex / DeepSeek-Harness 的桌面智能体客户端）
> 目标形态：Electron + TypeScript 桌面应用，具备「编码 / 识图 / 浏览器操控」等 agent 能力。
> 文档定位：界定**整体产品边界**、**技术架构**与**工程规范**，作为各阶段开发与评审的基准。第一阶段（页面样式 + 会话系统）可执行计划见《02-第一阶段计划.md》。

---

## 1. 项目定位与产品愿景

- **一句话**：一个连接 DeepSeek / Kimi 等开放模型 API 的**桌面 AI 智能体客户端**，能在本地完成编码、识别图片、操控浏览器等任务，并提供沉浸式的 IDE 类工作界面。
- **对标对象**：OpenAI Codex、DeepSeek-Harness、Cursor 等 agent 型开发工具。
- **覆盖平台**：桌面（Windows / macOS / Linux），以 Electron 实现。
- **交互形态**：左侧会话列表 + 中间对话主区 + 右侧代码 / 终端 / 任务 / 日志工作区（参见 `docs/design-ref.png` 设计稿）。

---

## 2. 总体目标与技术栈

| 维度 | 选型 |
| --- | --- |
| 桌面框架 | **Electron**（主进程 + 渲染进程 + preload） |
| 前端框架 | **React + TypeScript** |
| 构建工具 | **electron-vite**（Vite 驱动，主/预加载/渲染三端一并构建、HMR） |
| 样式 | **Tailwind CSS**（原子类）+ 成熟组件库（推荐 headless 组件库，与 Tailwind 融合；备选 Mantine） |
| 状态管理 | **Zustand**（轻量、适合会话/UI 状态） |
| 本地持久化 | **mysql2（MySQL）** 优先，自动建库建表；连不上**自动回退内存存储** |
| 代码高亮 | highlight.js / Shiki（后期可上 Monaco 编辑器） |
| 打包发布 | **electron-builder** |
| 代码质量 | ESLint + Prettier + TypeScript `strict`；Commit 规范 Conventional Commits |

> 说明：本产品是高度定制的深色 IDE 风界面，**以 Tailwind 为主力、以 headless 组件库提供无障碍与交互基元**，避免整套重型组件库的默认样式与深色主题冲突。

## 3. 开发边界（范围管理）

### 3.1 能力总览（全生命周期目标）

| 能力 | 说明 | 阶段 |
| --- | --- | --- |
| 对话 & 会话 | 多会话、本地持久化、历史检索 | P1 |
| 页面样式 | 主界面（左栏 + 对话主区 + 状态栏）+ 主题切换 | P1 |
| 模型接入 | 接入 DeepSeek / Kimi 等 OpenAI 兼容 API，流式对话 | P2 |
| Agent 工具编排 | 工具调用链、执行计划、进度展示 | P2/P3 |
| 编码能力 | 文件树、代码编辑器、文件读写、终端执行 | P3 |
| 识图能力 | 图片输入 + 多模态模型理解 | P3 |
| 浏览器操控 | 通过浏览器自动化（如 Playwright / Chrome DevTools）执行任务 | P4 |

### 3.2 当前（P1）边界

**做什么**
- 完整还原设计稿的主界面与样式（左栏 + 对话主区 + 全局状态栏、深色主题、交互态）。
- 流畅的**对话与会话系统**：新建/切换/删除/重命名/搜索会话，消息录入、渲染、滚动、编辑与删除；本地持久化。
- **主题切换**：设置页内多套预设主题（深/浅）+ **自定义背景色 / 文字颜色 / 强调色**，实时应用并持久化。

**不做什么（明确排除，避免蔓延）**
- 不接入任何真实模型 API，不做流式 AI 回答（P2 再做）。
- **右侧「代码/终端/任务/日志」工作区 P1 不做**（含文件树/编辑器/终端/状态栏文件信息），回归 P3。
- 不做真实的文件系统读写、代码执行、终端、浏览器操控（P3/P4）。
- 不做插件系统、账号登录、云同步、多端协作。
- 不做国际化、无障碍（可选加）、性能大改（后续阶段）。

> **边界原则**：目标「界面可交付、交互手感好、数据可留」。任何需要真实外部能力的功能一律后置到对应阶段。
>
> **参考**：代码编写相关模型调用可参考 [DeepSeek API 文档](https://api-docs.deepseek.com/zh-cn/)（P3 编码阶段落地）。

## 4. 总体架构（Electron 进程模型）

```
┌──────────────────────────────────────────────────────────┐
│ Electron Main Process（主进程，Node.js）                  │
│  · 应用生命周期 / 窗口管理 / 菜单 / 托盘 / 快捷键        │
│  · 所有 Node/系统能力：MySQL(mysql2)、文件、             │
│    子进程、模型 API 请求(主进程发起)                       │
│  · 唯一可访问系统资源的层                                 │
└───────────────┬──────────────────────────────────────────┘
                │ IPC (contextBridge 暴露的受控 API)
┌───────────────▼──────────────────────────────────────────┐
│ Preload（预加载脚本）                                    │
│  · contextBridge.exposeInMainWorld('agent', ...)         │
│  · 只暴露白名单 API，不透传 node/electron 全局            │
└───────────────┬──────────────────────────────────────────┘
                │ typed messages
┌───────────────▼──────────────────────────────────────────┐
│ Renderer（渲染进程，React + TS + Tailwind）              │
│  · UI / 状态(Zustand) / 会话与消息渲染 / 交互            │
│  · 不直接触碰 Node/MySQL/文件，全部经 IPC               │
└──────────────────────────────────────────────────────────┘
```

**关键安全约束（强制）**
- `nodeIntegration: false`；`contextIsolation: true`。
- 渲染进程**只**通过 preload 暴露的白名单 API 访问系统能力。
- 后续设置合理 `Content-Security-Policy`。
- IPC 入参做类型与 schema 校验，避免运行时注入。

## 5. 目录结构规范

```
AIAGENT-New/
├─ electron.vite.config.ts        # electron-vite 主/preload/renderer 配置
├─ package.json
├─ tsconfig.json / tsconfig.node.json / tsconfig.web.json
├─ tailwind.config.cjs
├─ src/
│  ├─ main/                       # 主进程
│  │  ├─ index.ts                 # 入口：创建窗口、生命周期
│  │  ├─ ipc/                     # IPC handler（session/message/model/window）
│  │  ├─ db/                      # mysql2(MySQL) + 内存兜底
│  │  │  ├─ index.ts              # DbStore 抽象 + initStore(选后端)
│  │  │  ├─ mysql.ts              # MySqlStore（连接/建库/建表/CRUD）
│  │  │  └─ memory.ts             # MemoryStore（降级兜底）
│  │  └─ services/                # 模型配置 + 模型流式调用（modelConfig/modelProvider）
│  ├─ preload/
│  │  ├─ index.ts                 # contextBridge 暴露 API
│  │  └─ index.d.ts               # window.agent 类型声明
│  └─ renderer/
│     ├─ index.html
│     └─ src/
│        ├─ main.tsx / App.tsx
│        ├─ styles/               # 全局样式 + tailwind 入口 + 主题令牌
│        ├─ theme/                # 主题预设 + buildTheme/applyTheme
│        ├─ stores/               # Zustand store（session/chat/ui/theme/model）
│        ├─ components/
│        │  ├─ layout/            # Sidebar / ChatPanel / SettingsPage / StatusBar / TitleBar / ResizeHandle
│        │  ├─ chat/              # 消息渲染（Blocks/RichText/MessageList/ChatInput/MarkdownRenderer）
│        │  ├─ sidebar/
│        │  └─ ui/                # 通用基础组件（Button/图标）
│        └─ lib/                  # 时间/深浅/转义工具
└─ shared/                        # 主/渲染共用类型、IPC channel 常量、schema
```

**规范要点**
- 主进程、preload、渲染进程类型尽量从 `shared/` 导入。
- `renderer` 内不出现 `node:*` / `electron` 直接引用（全部经 `window.agent`）。
- 组件层级尽量浅；公共组件放 `components/ui`，页面级组合组件放各 feature 目录。

## 6. 命名与代码规范

### 6.1 命名
| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 组件 | PascalCase，文件与组件同名 | `SessionListItem.tsx` |
| hooks | `use` 前缀 + camelCase | `useAutoScroll.ts` |
| store | `xxxStore` | `sessionStore.ts` |
| IPC channel | `域:动作`（冒号分隔，kebab） | `session:list`、`message:send` |
| TS 类型 | PascalCase | `SessionDto`、`IpcResult` |
| DB 表 | 复数小写下划线 | `sessions`、`messages` |
| 常量 | UPPER_SNAKE | `MAX_SESSION_TITLE` |

### 6.2 语言与格式
- TypeScript 开启 **`strict`**，禁用 `any`（确需时用 `unknown`）。
- 统一 **Prettier**（单引号、行宽 100、尾部逗号 all）。
- ESLint 以 `typescript-eslint` 推荐集 + `react-hooks` 插件。
- IPC 一律返回结构化 `IpcResult`，不裸抛异常穿透。

## 8. 状态管理规范

- 单一来源：每个领域一个 Zustand store，避免跨 store 互相写。
- 派生状态用 selector / `useMemo` 计算，不在 store 冗余。
- 异步副作用（IPC 调用、DB 读写）集中在 action 中。
- UI 态（拖拽、面板折叠）与数据态（sessions/messages）分离。

---

## 9. 数据模型规范（P1 落地）

```ts
interface Session { id; title; projectPath?; pinned; createdAt; updatedAt }
interface Message {
  id; sessionId; role: 'user'|'assistant'|'system'|'tool'
  content; blocks?: MessageBlock[]; status: 'pending'|'streaming'|'done'|'error'; timestamp
}
type MessageBlock =
  | { kind:'text'; content }
  | { kind:'thinking'; content; seconds? }
  | { kind:'plan'; items: PlanItem[] }
  | { kind:'files'; files: GeneratedFile[] }
  | { kind:'code'; language; code; filename? }
```

**约束**
- 时间统一 epoch ms；UUID 主键；`messages` 建 `(sessionId, timestamp)` 索引。

---

## 10. IPC 通信规范

- channel 常量集中在 `shared/ipc.ts`。
- **IPC 返回结构**：`IpcResult<T> = { ok:true; data } | { ok:false; error:{code,message} }`。
- 入参用 zod/手动校验；大 payload（消息流）用 `webContents.send` 推送，不阻塞 invoke。
- **命名**：`域:动作`，如 `model:getConfig` / `model:test`。

---

## 11. 错误处理与日志规范

- **分层**：主进程捕获异常 → 转 `IpcResult`；渲染层统一处理。
- **日志**：主进程打印 `[model] request/response/stream done` **不含 prompt / 响应内容**。
- **绝不静默**：网络/DB 失败必须有用户可见提示。

---

## 12. 持久化规范（MySQL，mysql2）

- **主后端**：主进程用 `mysql2` 连接本机 MySQL（`MYSQL_HOST/PORT/USER/PASSWORD/DATABASE`）。
- **自动建库建表**：先 `CREATE DATABASE IF NOT EXISTS`，再用连接池建表。
- **降级兜底**：连接失败自动回退内存存储（`MemoryStore`）。
- **SQL 安全**：全部参数化，禁止拼接。
- 时间戳 `BIGINT` 存 epoch ms；外键 `ON DELETE CASCADE`。

---

## 13. 构建、打包与发布规范

- **开发**：`electron-vite dev`（三端 HMR）。
- **构建**：`electron-vite build` → `electron-builder` 产出安装包（Win nsis / macOS dmg / Linux AppImage）。
- **版本**：SemVer。
- MySQL 连接信息走环境变量/配置，不入包。

---

## 14. 测试与质量保障

- **单测**：Vitest，重点覆盖 store / repos（`:memory:`）/ IPC 校验。
- **组件测试**：@testing-library/react。
- lint/prettier 进 pre-commit。

---

## 15. 源码到规范变更流程

- 任何新增能力先改本规范 + 对应阶段计划，再动代码。
- 跨层行为（IPC 契约、DB schema、共享类型）变更必须同步更新 `shared/`。

## 16. 阶段划分总览（Roadmap）

| 阶段 | 主题 | 关键交付 | 依赖 |
| --- | --- | --- | --- |
| **P1** | 页面样式 + 会话系统 | 主界面还原(左栏+对话区+状态栏)；主题切换；会话/消息持久化与交互；Mock 对话 | 无外部依赖 |
| **P2** | 模型接入 + 流式对话 | 多模型 API(OpenAI 兼容)、流式渲染、会话续接、上下文长度 | P1 |
| **P3** | Agent 编码能力 | 文件树、编辑器、FS 读写、终端执行、工具编排、识图 | P1/P2 |
| **P4** | 浏览器操控 + 集成 | 浏览器自动化、任务/日志增强、打包发布 | P2/P3 |

> P1 完成；P2 能力（识图 / 文档解析 / 联网搜索 / 回复样式优化）已实现；后续根据确认逐步推进 P3 / P4。
