# 08 · P3 Agent 执行内核威胁模型

## 1. 目的与安全结论

P3 会引入项目读取、补丁、命令、Docker、Git 和 Skills。任何模型输出、项目内容、Skill、
命令输出或 renderer 数据都不能直接获得系统能力。唯一可信的安全决策点是主进程内的确定性
Policy Engine；真实执行由受限后端完成，宿主写入由 Workspace Service 单独把关。

M0 只冻结契约、状态机、事件和测试夹具，不接入真实文件写入或命令执行。

## 2. 需要保护的资产

- 用户项目源码、未提交修改、二进制资产和 Git 历史。
- API Key、数据库密码、Git/SSH 凭据、浏览器数据和宿主环境变量。
- 宿主文件系统、进程、网络、Docker daemon 与其他容器。
- 用户批准的真实性、作用域和时效性。
- task/tool call/event/audit 的完整性与顺序。
- 应用可用性：主进程、磁盘、内存、CPU、PID 和临时空间。

## 3. 信任边界

1. **Renderer → Preload → Main**：renderer 视为可被 XSS 或依赖污染控制；只接受窄 IPC，
   每项入参运行时校验并验证 sender。
2. **模型/Skill/项目 → Tool Registry**：均为不可信建议；只有当前任务公开的原生 tool call
   才能进入 Registry，未知工具、重复 call ID 和异常参数先拒绝。
3. **Main → Local/Docker Backend**：后端只接受结构化 executable + argv，不接受 shell 字符串；
   后端不能自行修改权限或批准状态。
4. **Docker → Host**：不挂载宿主工作区为读写目录，不暴露 Docker socket、密钥或宿主网络；
   只导出受校验的补丁和产物清单。
5. **Sandbox patch → Host workspace**：批准令牌绑定精确补丁与基线哈希；写入前再次检查路径和哈希。

## 4. 攻击者能力与入口

- 恶意或被提示注入的模型构造危险 tool call、重复 call ID、超深/超大参数。
- 恶意仓库通过 README、代码注释、文件名、链接、依赖脚本和 Git 数据诱导越权。
- 恶意 Skill 声称拥有额外工具、伪造批准或要求泄漏密钥。
- 被控制的 renderer 伪造 task、workspace、批准或执行参数。
- 命令通过 shell 元字符、cwd、env、链接竞态、子进程和后台进程逃逸。
- 容器尝试访问宿主网关、metadata、Docker socket、设备或耗尽资源。
- 应用崩溃、超时、窗口关闭或会话删除造成孤儿任务与半写文件。

## 5. 强制缓解措施

- deny-first Policy Engine；模型和 Skill 永远不能批准操作或改变权限/环境。
- WorkspaceGrant 使用主进程生成的 ID；所有路径 realpath、根包含和链接检查在使用前复验。
- Tool Registry 白名单、运行时 schema、深度/节点限制、任务内 call ID 去重。
- 单调 task event sequence；显式终止态；超时、停止、窗口/会话生命周期统一取消。
- 批准令牌绑定 task、call/命令前缀、workspace、backend、参数摘要，短期且单次消费。
- Docker 默认断网、非 root、限资源、drop capabilities、no-new-privileges、无 RW 宿主挂载。
- Local Backend 使用独立 utility process、`shell=false`、最小环境和整棵进程树终止。
- 宿主写回只接受用户看到并批准的精确 diff；基线变化、补丁变化或链接变化立即中止。
- 审计日志仅记录决策元数据；prompt、回复、环境变量、Authorization 和密钥统一脱敏。
- 临时文件 + 原子替换；崩溃启动回收只处理带本应用 task 标识的资源。

## 6. 不由 M0 解决的风险

- M1 实现真实路径、junction/reparse point 与 TOCTOU 防护。
- M3 实现完整权限矩阵、命令分类和防重放批准令牌。
- M4/M5 分别验证本机进程树与 Docker 隔离。
- M7 实现补丁哈希绑定、原子写回和恢复备份。
- M10 在执行能力迁出 renderer 后开启 `sandbox: true` 并做完整回归。

任一后续里程碑无法证明上述边界时必须停线，不允许用 UI 提示代替安全约束。
