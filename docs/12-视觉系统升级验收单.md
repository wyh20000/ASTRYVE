### 已修复的测试不稳定问题（先前存在）

`pluginInstaller.test.ts` 的
"rejects excessive entry counts, total expanded size and suspicious compression ratios"
曾在本机全量并行时报 `Test timed out in 15000ms`（该文件 6~17s），单独运行通过（约 0.85s）。

**诊断结论（专项排查）**：

- 失败模式是**超时**，不是断言失败；把超时提到 60s 后全量立刻 877/877 通过；
- 根因是该用例会做**约 1000 次真实文件创建/删除 + 27MB 真实落盘**，
  而生产代码是「一条目一次 await 写盘」的顺序 I/O。多文件并发打满 CPU 时，
  每次 await 的调度延迟被放大：抽取阶段 358ms → 10662ms（28 倍），
  而同负载下纯 CPU 循环只慢 1.36 倍 —— 属于**延迟放大而非算力不足**；
- **不是产品缺陷**：`pluginInstaller.ts` 中没有任何 `Date.now` /
  `performance.now` / `setTimeout`，全部是确定性体积判断，
  慢机器不会误拒合法包；
- **不是临时目录冲突**：每个用例都用 `mkdtemp` 独立目录。

**处理方式**：在 `vitest.config.mts` 设 `maxWorkers: 1` + `fileParallelism: false`（串行）。

先试过 `maxWorkers: 4`：`pluginInstaller` 从 17s 降到 1.15s，一度全绿。
但随后发现同类问题**不止一个**——`localCommand.test.ts`（真实子进程 + 独立 stdio）
在 4 worker 下也会失败（单独运行 385ms 通过）。因此把并发降到 1，
彻底移除文件系统与进程调度的延迟放大。

不采用「只把超时调大」：这些用例耗时随负载漂移（0.5s~15s），调大只是推迟问题。

**代价**：全量耗时约 20s → **约 72s**。这是有意用时间换确定性；
测试本身不慢，慢的是并发争用。

**验证**：连续两次全量均为 **121 文件 / 888 测试通过**，
耗时 71.74s / 71.75s，`pluginInstaller` 866ms、`localCommand` 345ms。

### 真实窗口验收 + 首帧颜色修复

**发现并修复的首帧缺陷**

`BrowserWindow.backgroundColor` 与 `titleBarOverlay` 原先**写死旧版深蓝**
（`#0a0e17` / `#a7b0c0`），而令牌已经改为中性冷灰 `#111315`。
这些值决定渲染进程应用主题**之前**的窗口底色，因此会闪一下旧配色。

修复方式不是就地改两个字面量，而是抽出单一来源：

- 新增 `src/shared/themePaint.ts` 导出 `FIRST_PAINT_BACKGROUND` / `FIRST_PAINT_SYMBOL`；
- `theme/tokens.ts` 的 `DARK_BASE.surfaceApp` / `textPrimary` **直接引用这两个常量**，
  因此不可能出现「令牌改了、首帧没改」的漂移；
- `main/index.ts` 的窗口背景与标题栏、`main/ipc/window.ts` 的兜底值使用同一常量；
- `src/shared/themePaint.test.ts` 断言这四个值与深色令牌完全一致。

**新增真实窗口验收：`npm run smoke:theme`**

单元测试里的 `document` 是 jsdom 假实现，只能证明「写入了正确的值」，
不能证明「真实 Electron 窗口渲染正确」（CSP 拦截、preload 注入、字体缺失、
首帧底色等都只有真实窗口才暴露）。因此新增一条真实窗口验收：

**一次真实的误判记录**

首次查看截图时，我认为侧栏会话文字「变成了青色」，怀疑令牌把中性文本染成了强调色。
但用真实窗口读取计算值后发现是 `rgb(168,176,184)` —— **完全中性**，
是低精度图片预览造成的误判（该用户保存的强调色确实是青色 `#31a08d`）。

我把这次教训变成了可执行断言：会话标题颜色必须是中性灰阶，
否则验收失败。这样以后真的被改坏时会被拦住。

### 保存按钮下方「白块」修复（用户反馈）

用户截图指出：模型编辑表单里「保存」按钮下方有一块白色。

**定位过程（两步都用了客观测量，没有靠猜）**

1. jsdom 里查不到问题 —— 测试环境不加载 CSS，`background-color` 全是
   `rgba(0,0,0,0)`，因此改为**对用户截图做逐像素扫描**。

2. 扫描「保存」按钮中心竖线（x=488），得到决定性证据：

```
y=796  #31a08d   按钮填充（强调色）
y=797  #d3e0dc   ← 近白，仅 2px，这就是用户看到的「白」
y=799  #202428   卡片背景
```

**根因：不是颜色问题，是几何问题。**

- 先假设 `--border-focus` 过亮 → 实测计算为 `#3ba593`（强调色向背景混合），
  并不刺眼，**该假设被推翻**；
- 真实成因：`outline: 2px` + `outline-offset: 2px`，聚焦环整体外扩 4px，
  在圆角按钮上只有**最外缘 2px** 露出来；该边缘像素被抗锯齿与卡片背景
  按约 0.4/0.6 混合 → `#3ba593` 与 `#202428` 混合 ≈ `#d3e0dc`，与实测一致。

**修复**：`outline-offset: 2px` → `0`。环完整贴合控件轮廓，
键盘焦点依然清晰可见，颜色与厚度均未改动。

**回归断言**：真实窗口验收新增「聚焦环 offset 必须为 0」的检查
（实测 `outlineOffset: "0px"`）。

### 强调色可读性修复 + Codex 风格主题卡片

**问题：实心按钮出现「蓝底黑字」**

用户反馈保存按钮「太丑了，尤其浅色的时候里面字是黑的」。

**排查（先量化再改）**：测算了所有预设强调色上白字/黑字的对比度：

| 强调色 | 白字 | 黑字 | `bestOn` 的选择 |
| --- | --- | --- | --- |
| 旧默认蓝 `#4d6bfe` | **4.33** ❌ | 4.85 | 黑 |
| 青 `#31a08d` | 3.21 ❌ | 6.54 | 黑 |
| 翠绿 `#3fb950` | 2.54 ❌ | 8.27 | 黑 |
| 琥珀 `#e08a3c` | 2.67 ❌ | 7.87 | 黑 |

**结论：`bestOn` 没有写错** —— 旧默认蓝上白字只有 4.33:1，不达 AA，
所以它选黑字是正确的可读性决策。**根因是强调色本身对白字不够深。**

**处理（三处）**

1. **默认强调色加深**：`#4d6bfe` → `#3b5bdb`，
   白字 **5.67:1**，Hover 7.10，Active 8.36 —— 既好看又达标。
   常量移至 `shared/themePaint.ts`，主进程首帧与渲染进程共用同一来源。
2. **交互态改为向黑派生**：原先深色模式向白派生，hover 会让白字对比度**下降**
   （4.33 → 3.45）。现在统一向黑派生，交互越深对比越高。
3. **`bestOn` 增加门槛语义**：候选顺序即优先级，返回第一个达标者；
   全不达标才退回最高者。
   修好过程中发现上一版兜底有缺陷：先取「对比度最高者」再判断是否达标，
   在首选不达标时仍可能返回未达标的首选（实测红底白字 4.00 被返回）。
   已写测试覆盖（红底必须改选黑字）。

**Codex 风格主题卡片**

**回归测试**：`ThemeModeCards.test.tsx` 9 项，覆盖语义、键盘、disabled、

### 按钮白色底边：真正的根因（第三次定位，这次找到了）

用户反馈：**非聚焦态**按钮下方有一条白块；聚焦时反而正常。

**关键突破**：在真实窗口里读取按钮的计算样式，直接拿到证据：

```
btnBg:        rgb(59, 91, 219)                    ← 颜色正确
btnBoxShadow: rgb(240, 245, 255) 0px 2px 0px 0px  ← 近白，向下偏移 2px
```

**这不是聚焦环**，而是 antd 6 按钮的「下沉阴影」。追到源码：

```
node_modules/antd/es/button/style/token.js:40
  primaryShadow: `0 ${token.controlOutlineWidth}px 0 ${token.controlOutline}`
```

即「向下偏移 `controlOutlineWidth`(2px)、颜色为 `controlOutline` 的**实心**阴影」。
`controlOutline` 默认由浅色板推导，在深色主题下呈现为近白的 `rgb(240,245,255)`——
于是按钮下方永远压着一条白边。聚焦时该阴影被 focus 样式覆盖，所以看起来"正常"，
这也解释了用户观察到的现象。

**修复**：把 `controlOutline` 指向应用背景色，`controlOutlineWidth` 保持 2。
实测阴影变为 `rgb(17,19,21)`（即 `--surface-app`），与背景融合、不再显形。
同时把 `boxShadow / boxShadowSecondary / boxShadowTertiary` 映射到本项目
按明暗派生的阴影，避免其余浮层在深色下偏浅。

**期间推翻的两个错误假设**（都靠测量否掉）：

1. 以为是 `outline-offset` 几何问题 —— 第二次扫描已修正为 0，但白条仍在；
2. 以为是 `boxShadowTertiary` —— 改写后实测阴影值分毫未变，说明猜错了 token。

**回归断言**：真实窗口验收新增「按钮阴影亮度不得 > 0.55」，
深色模式下再出现近白阴影会直接失败。

### 缩略图铺满可点区域，标签移到高亮区之外

原先「卡片 = 带内边距的容器，图片与文字都在里面，hover/选中作用于整块」。
现在拆成两层：

```

    <img />
  </span>
  <span>标签 + 对勾</span>       ← 在高亮区之外
</button>
```

效果：

- 图片边缘即高亮区边缘（`span` 不设 `p-*`）；
- 边框从 `<img>` 移到缩略图层，选中态蓝框正好贴合图片边缘；
- hover 只高亮图片区域，不会把标签一起"染色"成一块。

**测试同步**：原三条针对 `button` 的边框断言改为针对缩略图层，
并新增一条约束「文字位于高亮区之外」（高亮层内不得含文本）。

### 本阶段发现并修复的真实缺陷

1. **antd 6 会在两个汉字之间自动插入空格**，按钮文案变成「保 存」。
   违反文档 4.3「中文不使用过宽字距」→ `Button` 显式 `autoInsertSpace={false}`。
2. **`TextArea` 的 `minRows` 泄漏为 DOM 属性**且覆盖默认值：
   `@rc-component/input` 只从 `autoSize` 对象读取 minRows/maxRows，
   顶层 `minRows` 既不生效还会触发 React 告警 → 改为同时写 `rows` 与 `autoSize`。
3. `TextAreaProps` 未从 `antd` 根导出，需从 `antd/es/input` 导入。

### 本阶段发现并修复的真实缺陷（续）

4. **`cssVar` 写法错误（严重）**：antd 6 的 `ThemeConfig.cssVar` 是
   `{ prefix?, key? }` **对象**，而代码里写的是 `cssVar: true`。
   之所以一直没被发现，是因为 `toAntdTheme` 的返回类型被标成了宽松的
   `Record<string, unknown>`，调用处又加了 `as never` —— 断言把类型检查整个关掉了。
   **修复**：`toAntdTheme` 拆分到 `theme/antdTheme.ts` 并把返回类型标注为 antd 的
   `ThemeConfig`，同时移除 `App.tsx` 中的 `as never`。
   现在任何主题字段写错都会在 `npm run typecheck` 阶段报错。

5. **`Card.colorBgContainer` 不是 Card 的组件级 token**：它只是全局 alias token。
   写进 `components.Card` 属于「塞了一个不存在的字段」，antd 静默忽略、不报错。
   **修复**：移除该覆盖，并补注释说明卡片背景走全局 `colorBgContainer`。

6. **`getDesignToken` 的能力边界被误判**：实测它只返回扁平 `AliasToken`，
   **不计算组件级 token**。因此不能用它断言组件级 token 的值。
   该结论已写入 `docs/13-组件API参考.md`。
