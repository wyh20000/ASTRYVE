### 已修复的测试不稳定问题（先前存在）

`pluginInstaller.test.ts` 的
"rejects excessive entry counts, total expanded size and suspicious compression ratios"
曾在本机全量并行时报 `Test timed out in 15000ms`（该文件 6~17s），单独运行通过（约 0.85s）。

**诊断结论（专项排查）**：

- 失败模式是**超时**，不是断言失败；把超时提到 60s 后全量立刻 877/877 通过；
- 根因是该用例会做**约 1000 次真实文件创建/删除 + 27MB 真实落盘**，
  而生产代码是「一条目一次 await 写盘」的顺序 I/O。多文件并发打满 CPU 时，
  每次 await 的调度延迟被放大：抽取阶段 358ms → 10662ms（28 倍），
  而同负载下纯 CPU 循环只慢 1.36 倍 —— 属于**延迟放大而非算力不足**；
- **不是产品缺陷**：`pluginInstaller.ts` 中没有任何 `Date.now` /
  `performance.now` / `setTimeout`，全部是确定性体积判断，
  慢机器不会误拒合法包；
- **不是临时目录冲突**：每个用例都用 `mkdtemp` 独立目录。

**处理方式**：在 `vitest.config.mts` 设 `maxWorkers: 1` + `fileParallelism: false`（串行）。

先试过 `maxWorkers: 4`：`pluginInstaller` 从 17s 降到 1.15s，一度全绿。
但随后发现同类问题**不止一个**——`localCommand.test.ts`（真实子进程 + 独立 stdio）
在 4 worker 下也会失败（单独运行 385ms 通过）。因此把并发降到 1，
彻底移除文件系统与进程调度的延迟放大。

不采用「只把超时调大」：这些用例耗时随负载漂移（0.5s~15s），调大只是推迟问题。

**代价**：全量耗时约 20s → **约 72s**。这是有意用时间换确定性；
测试本身不慢，慢的是并发争用。

**验证**：连续两次全量均为 **121 文件 / 888 测试通过**，
耗时 71.74s / 71.75s，`pluginInstaller` 866ms、`localCommand` 345ms。

### 真实窗口验收 + 首帧颜色修复

**发现并修复的首帧缺陷**

`BrowserWindow.backgroundColor` 与 `titleBarOverlay` 原先**写死旧版深蓝**
（`#0a0e17` / `#a7b0c0`），而令牌已经改为中性冷灰 `#111315`。
这些值决定渲染进程应用主题**之前**的窗口底色，因此会闪一下旧配色。

修复方式不是就地改两个字面量，而是抽出单一来源：

- 新增 `src/shared/themePaint.ts` 导出 `FIRST_PAINT_BACKGROUND` / `FIRST_PAINT_SYMBOL`；
- `theme/tokens.ts` 的 `DARK_BASE.surfaceApp` / `textPrimary` **直接引用这两个常量**，
  因此不可能出现「令牌改了、首帧没改」的漂移；
- `main/index.ts` 的窗口背景与标题栏、`main/ipc/window.ts` 的兜底值使用同一常量；
- `src/shared/themePaint.test.ts` 断言这四个值与深色令牌完全一致。

**新增真实窗口验收：`npm run smoke:theme`**

单元测试里的 `document` 是 jsdom 假实现，只能证明「写入了正确的值」，
不能证明「真实 Electron 窗口渲染正确」（CSP 拦截、preload 注入、字体缺失、

| 断言 | 实测值 |
| --- | --- |
| `--surface-app` 为合法 hex | `#111315` |
| 字体栈包含微软雅黑 | `"Microsoft YaHei", "微软雅黑", …` |
| `body` 字号为 14px | `14px` |
| 明暗主题生效 | `colorScheme: dark`、`.dark` 类存在 |
| `#root` 已挂载（CSP/preload 正常） | `childElementCount: 1` |
| **DOM 中不存在小于 14px 的可见文字** | `[]` |
| **会话标题未被强调色污染** | `rgb(230,232,234)`（当前行为选中态主色） |

并输出 `out/theme-smoke-<mode>.png` 截图供人工复核。

**一次真实的误判记录**

首次查看截图时，我认为侧栏会话文字「变成了青色」，怀疑令牌把中性文本染成了强调色。
但用真实窗口读取计算值后发现是 `rgb(168,176,184)` —— **完全中性**，
是低精度图片预览造成的误判（该用户保存的强调色确实是青色 `#31a08d`）。

我把这次教训变成了可执行断言：会话标题颜色必须是中性灰阶，
否则验收失败。这样以后真的被改坏时会被拦住。

### 阶段 C · 7.3 输入区迁移到受控 `Sender`

**交付物**：`src/renderer/src/components/chat/ChatInput.tsx`

**迁移方式**：外壳换成 Ant Design X 的 `Sender`，但 `value` / `onChange`
仍由本组件持有，`onSubmit` 直接调用既有 `doSend`（内部仍是
`chatStore.send(sessionId, content, attachments)`）：

| 能力 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 输入框 | 自制 autosize `<textarea>` | `Sender`（`autoSize` + `submitType="enter"`） |
| Enter / Shift+Enter | 自己在 `onKeyDown` 里发消息 | 交给 `Sender`，本组件不再处理 Enter（避免双发） |
| 发送 / 停止 | 自制 `h-8 w-8` 圆形按钮 | `components.SendButton` / `components.LoadingButton` |
| 附件与解析状态、插件 mention | 边框容器内 | `header` 插槽（位置与外观不变） |
| 模型选择、附件/图片入口 | 底部工具条 | `footer` 插槽（`suffix={false}` 关掉默认操作区） |
| 描边 / 背景 / 焦点态 | 容器 `focus-within:border-accent` | 不变，仍在外层容器上（`styles.root` 关掉组件自带边框与阴影） |

**三个必须知道的组件行为**（详细出处见 `docs/13-组件API参考.md`）：

1. `Sender` 的 Enter 提交只看 `onKeyDown` 的**返回值是否为 `false`**，
   `preventDefault()` 不阻止提交 → `/Skill`、`@插件` 菜单里用回车选中时
   必须 `return false`，否则「选中菜单项」的同一次回车里还会再发一次消息。
2. `submitDisabled` 只由 **`SendButton`** 通过 `setSubmitDisabled` 反向同步
   （`es/sender/Sender.js:179` + `components/ActionButton.js:20-24`）。
   若把默认操作区换成自己的按钮，这个状态会永远停在初始值、**回车再也不发送**。
   因此本项目用 `suffix={false}`，并在 `footer` 里显式渲染
   `components.SendButton`，把 `disabled={!canSend}` 传给它。
3. `mergedDisabled = props.disabled ?? rootDisabled ?? onSendDisabled`
   （`ActionButton.js:19`）。显式 `disabled` 优先，所以「只有附件、没有文字」
   时也能发送（迁移前的能力，靠这一条保住）。

**保持不变的业务行为（全部有测试）**：

- Enter 发送、Shift+Enter 换行；一次回车只发送一次（新增断言）；
- `/Skill` 与 `@插件` 菜单：键盘 ↑/↓ + 回车/Tab 选中、Esc 关闭、
  点击输入框本身不关闭、点击外部关闭；选中后把光标放到文本末尾；
  **菜单里回车不会顺手把消息发出去**（新增断言）；

### 保存按钮下方「白块」修复（用户反馈）

用户截图指出：模型编辑表单里「保存」按钮下方有一块白色。

**定位过程（两步都用了客观测量，没有靠猜）**

1. jsdom 里查不到问题 —— 测试环境不加载 CSS，`background-color` 全是
   `rgba(0,0,0,0)`，因此改为**对用户截图做逐像素扫描**。

2. 扫描「保存」按钮中心竖线（x=488），得到决定性证据：

```
y=796  #31a08d   按钮填充（强调色）
y=797  #d3e0dc   ← 近白，仅 2px，这就是用户看到的「白」
y=799  #202428   卡片背景
```

**根因：不是颜色问题，是几何问题。**

- 先假设 `--border-focus` 过亮 → 实测计算为 `#3ba593`（强调色向背景混合），
  并不刺眼，**该假设被推翻**；
- 真实成因：`outline: 2px` + `outline-offset: 2px`，聚焦环整体外扩 4px，
  在圆角按钮上只有**最外缘 2px** 露出来；该边缘像素被抗锯齿与卡片背景
  按约 0.4/0.6 混合 → `#3ba593` 与 `#202428` 混合 ≈ `#d3e0dc`，与实测一致。

**修复**：`outline-offset: 2px` → `0`。环完整贴合控件轮廓，
键盘焦点依然清晰可见，颜色与厚度均未改动。

**回归断言**：真实窗口验收新增「聚焦环 offset 必须为 0」的检查
（实测 `outlineOffset: "0px"`）。

### 聚焦反馈统一 + 插件分类移除

**聚焦反馈的第三次调整（前两次记录见上）**

用户在修复「白块」后继续反馈：按钮聚焦时仍像「被描了一圈边」。

实测确认两件事：

1. `outlineColor = rgb(77,107,254)`，即 `--border-focus` 的正常取值

2. 真正显重的原因是 antd 按钮**另有一层自己的 focus 阴影**，

### 强调色可读性修复 + Codex 风格主题卡片

**问题：实心按钮出现「蓝底黑字」**

用户反馈保存按钮「太丑了，尤其浅色的时候里面字是黑的」。

**排查（先量化再改）**：测算了所有预设强调色上白字/黑字的对比度：

| 强调色 | 白字 | 黑字 | `bestOn` 的选择 |
| --- | --- | --- | --- |
| 旧默认蓝 `#4d6bfe` | **4.33** ❌ | 4.85 | 黑 |
| 青 `#31a08d` | 3.21 ❌ | 6.54 | 黑 |
| 翠绿 `#3fb950` | 2.54 ❌ | 8.27 | 黑 |
| 琥珀 `#e08a3c` | 2.67 ❌ | 7.87 | 黑 |

**结论：`bestOn` 没有写错** —— 旧默认蓝上白字只有 4.33:1，不达 AA，
所以它选黑字是正确的可读性决策。**根因是强调色本身对白字不够深。**

**处理（三处）**

1. **默认强调色加深**：`#4d6bfe` → `#3b5bdb`，
   白字 **5.67:1**，Hover 7.10，Active 8.36 —— 既好看又达标。
   常量移至 `shared/themePaint.ts`，主进程首帧与渲染进程共用同一来源。
2. **交互态改为向黑派生**：原先深色模式向白派生，hover 会让白字对比度**下降**
   （4.33 → 3.45）。现在统一向黑派生，交互越深对比越高。
3. **`bestOn` 增加门槛语义**：候选顺序即优先级，返回第一个达标者；
   全不达标才退回最高者。
   修好过程中发现上一版兜底有缺陷：先取「对比度最高者」再判断是否达标，
   在首选不达标时仍可能返回未达标的首选（实测红底白字 4.00 被返回）。
   已写测试覆盖（红底必须改选黑字）。

**Codex 风格主题卡片**

按用户要求参考 Codex 的「外观」页，把原来的分段控件换成**三张可视化卡片**。

- 每张卡片渲染该模式的**真实令牌缩略图**（应用背景 / 侧栏 / 内容卡 /
  文字条 / 强调色按钮），颜色由 `resolveTheme` 解析得到，不是硬编码色块；
- `跟随系统` 卡片额外展示「当前：浅色 / 深色」，反映实际生效结果；
- 语义为 `radiogroup` + `radio` + `aria-checked`，支持 Tab 与 Enter；
- 每张卡片有显式 `aria-label`（`主题模式：浅色`），
  避免与卡片内文本拼成歧义名称（这曾导致测试查询命中两张卡）。

**回归测试**：`ThemeModeCards.test.tsx` 9 项，覆盖语义、键盘、disabled、
以及「深/浅缩略图颜色必须不同」「跟随系统缩略图随系统明暗变化」
（后者确保缩略图真的来自令牌而非硬编码）。

### 按钮白色底边：真正的根因（第三次定位，这次找到了）

用户反馈：**非聚焦态**按钮下方有一条白块；聚焦时反而正常。

**关键突破**：在真实窗口里读取按钮的计算样式，直接拿到证据：

```
btnBg:        rgb(59, 91, 219)                    ← 颜色正确
btnBoxShadow: rgb(240, 245, 255) 0px 2px 0px 0px  ← 近白，向下偏移 2px
```

**这不是聚焦环**，而是 antd 6 按钮的「下沉阴影」。追到源码：

```
node_modules/antd/es/button/style/token.js:40
  primaryShadow: `0 ${token.controlOutlineWidth}px 0 ${token.controlOutline}`
```

即「向下偏移 `controlOutlineWidth`(2px)、颜色为 `controlOutline` 的**实心**阴影」。
`controlOutline` 默认由浅色板推导，在深色主题下呈现为近白的 `rgb(240,245,255)`——
于是按钮下方永远压着一条白边。聚焦时该阴影被 focus 样式覆盖，所以看起来"正常"，
这也解释了用户观察到的现象。

**修复**：把 `controlOutline` 指向应用背景色，`controlOutlineWidth` 保持 2。
实测阴影变为 `rgb(17,19,21)`（即 `--surface-app`），与背景融合、不再显形。
同时把 `boxShadow / boxShadowSecondary / boxShadowTertiary` 映射到本项目
按明暗派生的阴影，避免其余浮层在深色下偏浅。

**期间推翻的两个错误假设**（都靠测量否掉）：

1. 以为是 `outline-offset` 几何问题 —— 第二次扫描已修正为 0，但白条仍在；
2. 以为是 `boxShadowTertiary` —— 改写后实测阴影值分毫未变，说明猜错了 token。

**回归断言**：真实窗口验收新增「按钮阴影亮度不得 > 0.55」，
深色模式下再出现近白阴影会直接失败。

### 缩略图铺满可点区域，标签移到高亮区之外

用户反馈：图片应占满 hover 区域，文字放在外面。

**结构调整**（`ThemeModeCards`）

原先「卡片 = 带内边距的容器，图片与文字都在里面，hover/选中作用于整块」。
现在拆成两层：

```
<button>                        ← 可点、可聚焦，无内边距、无边框
  <span 缩略图层>               ← hover / 选中态作用于此，图片铺满
    <img />
  </span>
  <span>标签 + 对勾</span>       ← 在高亮区之外
</button>
```

效果：

- 图片边缘即高亮区边缘（`span` 不设 `p-*`）；
- 边框从 `<img>` 移到缩略图层，选中态蓝框正好贴合图片边缘；
- hover 只高亮图片区域，不会把标签一起"染色"成一块。

**测试同步**：原三条针对 `button` 的边框断言改为针对缩略图层，
并新增一条约束「文字位于高亮区之外」（高亮层内不得含文本）。

### 重大发现：官方插件市场同步一直失败（真 bug，已修）

排查「Codex 的插件图标是怎么来的」时，发现的问题比样式更严重。

**图标机制（查清后的结论）**

| 环节 | 事实 |
| --- | --- |
| 插件索引 | `raw.githubusercontent.com/openai/plugins/main/.agents/plugins/marketplace.json`，只有 `name` / `source` / `policy` / `category`，**不含图标** |
| 图标来源 | 每个插件的清单 `plugins/<name>/.codex-plugin/plugin.json` 里的 `interface` 块 |
| 图标字段 | `logo` / `logoDark` / `composerIcon` / `brandColor` |
| 取 SHA | 用仓库 main 的 commit SHA 把清单与资源固定到不可变版本 |
| 本项目的解析 | `pluginMarketplace.ts` 已完整实现上述提取，渲染端由 `PluginLogo` 使用 |

**但实测发现：65 个条目的 `logoUrl` / `brandColor` 全为空。**

根因定位到同步本身失败：

```
source "Codex official" error = "Codex 官方版本超过大小限制"
条目数 = 0
```

读取 main 分支 SHA 时用了 GitHub 的**完整 commit 对象**端点：

| 端点 | 实测响应 | 代码上限 |
| --- | --- | --- |
| `GET /repos/openai/plugins/commits/main`（旧） | **475.3 KB** | 256 KB → **必然抛错** |
| `GET /repos/openai/plugins/git/ref/heads/main`（新） | **0.3 KB** | sha 完全一致 |

也就是说，**官方插件市场从来没有同步成功过**；界面上看到的条目是更早版本留下的旧缓存。

**修复**：改用 `git/ref` 端点取 SHA，其余校验（40 位十六进制、禁止 redirect、
大小上限、清单解析路径）完全不变。

**修复后实测（真实运行时，非单测）**

```
[market-diag] 条目数: 65
[market-diag] logoUrl: 57   composerIconUrl: 55   brandColor: 47
[market-diag] atlassian-rovo brand=#0052CC logo=Y
```

真实窗口内统计插件 Logo 渲染：

```
totalImgs: 58, remoteLogoImgs: 58, loaded: 58, broken: 0
```

**58 个 Logo 全部加载成功，0 个失败**（此前全部回退成通用占位图标，
这也是插件页显得"简陋"的直接原因之一）。

**同步影响的测试**：`pluginMarketplace.test.ts` 的 fetcher mock 由
`{ sha }` 改为 `{ object: { sha } }`，与新端点结构一致。

> 排查方法备注：`npm run smoke:market` 会真实同步一次官方市场并输出
> 条目数 / 图标数 / 品牌色数，是这条链路的可复用验证入口。

### 本阶段发现并修复的真实缺陷

1. **antd 6 会在两个汉字之间自动插入空格**，按钮文案变成「保 存」。
   违反文档 4.3「中文不使用过宽字距」→ `Button` 显式 `autoInsertSpace={false}`。
2. **`TextArea` 的 `minRows` 泄漏为 DOM 属性**且覆盖默认值：
   `@rc-component/input` 只从 `autoSize` 对象读取 minRows/maxRows，
   顶层 `minRows` 既不生效还会触发 React 告警 → 改为同时写 `rows` 与 `autoSize`。
3. `TextAreaProps` 未从 `antd` 根导出，需从 `antd/es/input` 导入。

### 本阶段发现并修复的真实缺陷（续）

4. **`cssVar` 写法错误（严重）**：antd 6 的 `ThemeConfig.cssVar` 是
   `{ prefix?, key? }` **对象**，而代码里写的是 `cssVar: true`。
   之所以一直没被发现，是因为 `toAntdTheme` 的返回类型被标成了宽松的
   `Record<string, unknown>`，调用处又加了 `as never` —— 断言把类型检查整个关掉了。
   **修复**：`toAntdTheme` 拆分到 `theme/antdTheme.ts` 并把返回类型标注为 antd 的
   `ThemeConfig`，同时移除 `App.tsx` 中的 `as never`。
   现在任何主题字段写错都会在 `npm run typecheck` 阶段报错。

5. **`Card.colorBgContainer` 不是 Card 的组件级 token**：它只是全局 alias token。
   写进 `components.Card` 属于「塞了一个不存在的字段」，antd 静默忽略、不报错。
   **修复**：移除该覆盖，并补注释说明卡片背景走全局 `colorBgContainer`。

6. **`getDesignToken` 的能力边界被误判**：实测它只返回扁平 `AliasToken`，
   **不计算组件级 token**。因此不能用它断言组件级 token 的值。
   该结论已写入 `docs/13-组件API参考.md`。

### 缺陷修复：思考过程「点开看不到」「展开了但里面空的」「动效太繁琐」

jsdom 没有布局与动画，这类问题在单测里看不见，因此临时在真实 Electron 窗口里
注入一条流式思考消息并真实点击状态行，读取**计算样式与盒子高度**
（探针已删除，只留结论）：

```
修复前（内联样式 = rc-motion 卡在进场起始态，1.5s 后仍未推进）
  class      : ant-motion-collapse-enter ant-motion-collapse-enter-start
  inline     : height: 0px; opacity: 0;
  computed   : height "0px"  opacity "0"      ← 面板是空的
  内容盒子    : h 50                        ← 文字其实在 DOM 里，只是被裁没了
  300ms 内 rAF: 1 帧                         ← 流式期间帧被推迟

修复后（同一环境、同一条消息）
  inline     : height: 0px; opacity: 0;      ← 动画仍卡着，但已不影响可见性
  computed   : height "62px" opacity "1" transition "none"
  内容盒子    : h 50  opacity 1  判定 visible: true
  点击收起    : 包装层立即消失（正文不再挂在 DOM 里）
```

**官方文档与源码核对（用户怀疑「用错了 API」）**

对照 [Think 组件文档](https://x.ant.design/components/think)（`expanded` / `onExpand` /
`destroyOnHidden` / `title` / `icon` / `loading` / `blink`）与官方
[`demo/expand.tsx`](https://github.com/ant-design/x/blob/main/packages/x/components/think/demo/expand.tsx)、
[`demo/destroyOnHidden.tsx`](https://github.com/ant-design/x/blob/main/packages/x/components/think/demo/destroyOnHidden.tsx)：
本项目的用法与官方示例**完全一致**（受控 `expanded` + `onExpand={(next) => ...}`），
不是 API 用错。问题出在**动画的推进依赖两帧 rAF**、以及**块列表重建丢状态**。

顺带记录一个官方写法：文档 `demo/status.tsx` 里「自定义旋转图标」是用
`loading={<SyncOutlined style={{ animation: 'spin 1s linear infinite' }} />}`
实现的（`loading` 接受 ReactNode）。本项目选择不传 `loading`、直接用 CSS 旋转
`Think` 自带图标，代价是依赖一个内部类名（已记入 docs/13）。

**实现**（`src/renderer/src/components/chat/Blocks.tsx`、`MessageItem.tsx`、
`src/renderer/src/styles/global.css`）

- 正文改成 `{open && <div …/>}`：收起时根本不在 DOM 里，展开时立即参与布局。
- `Think` 根节点加 `.thinking-panel` 标记，`global.css` 里两条规则接管可见性：
  ```css
  .thinking-panel .ant-motion-collapse-enter { height: auto !important; opacity: 1 !important; transition: none !important; }
  .thinking-panel .ant-motion-collapse-leave { display: none !important; }
  ```
  内联样式必须用 `!important` 才能覆盖（与本仓库既有的 antd 覆盖问题同源），
  选择器出处见 docs/13。
- `Blocks` 的 key 从下标改为 `${kind}-${同类序号}`；思考展开状态自持或由
  `MessageItem` 受控传入。`ThinkingBlock` 不再接 `seconds`，也不再自行计时。
- 没有引入重挂载（`key` 换状态会连带把标题行的 `<button>` 换掉、键盘焦点丢失），
  也没有复制 `Think` 的内容区样式，改动保持在两处。

**动效**（`src/renderer/src/styles/global.css`）

```css
.thinking-streaming .ant-think-status-icon { animation: thinking-spin 1.1s linear infinite; }
@keyframes thinking-spin { to { transform: rotate(360deg); } }
```

选择器出处：`@ant-design/x` 的 `Think` 用 `${prefixCls}-status-icon`
作为图标容器（`node_modules/@ant-design/x/es/think/Think.js:101`，已记入 docs/13）。
`.thinking-dots` 规则随之删除（`.reply-dots` 保留，`MessageItem` 仍在用），
reduced-motion 里改成关掉这段旋转。
