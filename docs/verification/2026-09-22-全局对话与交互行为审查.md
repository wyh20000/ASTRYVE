# ASTRYVE 全局对话与交互行为审查

> 审查基线：`1a466eb`
>
> 审查日期：2026-09-22
>
> 范围：会话创建与切换、输入与附件、消息发送、模型/搜索/Skill/插件/项目/Chrome 路由、原生工具循环、审批与补充提问、流式时间线、错误与取消、历史上下文、图片、持久化和恢复。
>
> 本文是代码审查结论，不表示问题已经修复。涉及 Google Chrome DevTools MCP 的目标架构以 `docs/superpowers/specs/2026-09-22-explicit-chrome-context-design.md` 为准。

## 1. 总结

当前对话系统已经具备流式消息、思考块、工具时间线、图片预览、文档解析、Skill、插件、项目工具、审批和多会话等主要组件，但各能力是在不同阶段分别接入的，导致“发送一次消息”没有统一的事务、路由和终态模型。

最影响使用的不是某个单独 UI，而是以下五类系统性问题：

1. **发送生命周期没有单一真相源。** Renderer 在 IPC 返回后才标记发送中，而主进程可能已经推送甚至完成回复；快速回复、初始化失败、重复回车、取消和任务替换都会产生竞态。
2. **能力路由彼此割裂。** 普通聊天默认联网、项目会话按关键词分流、Chrome 由正则开启、图片又关闭全部工具，Skill/插件各自解析，行为难以预测。
3. **跨轮上下文不完整。** 文档正文、纯工具证据、历史图片、失败终态和长对话裁剪使用不同规则，第二问可能拿不到第一问真实使用的证据。
4. **会话 UI 状态没有按 session 隔离。** 文本被直接清空，附件和异步解析却可能跨会话残留；滚动位置、等待提问和后台审批也缺少清晰归属。
5. **本地持久化不适合长对话和图片。** 已登录用户默认使用整库 JSON 文件，每次流式持久化都会重新序列化全部会话和 Base64 图片，数据量增长后会明显拖慢对话。

建议先修生命周期和上下文 P1，再实施模型驱动的统一能力循环。不要先做大规模视觉改版；否则界面会变，但最影响可靠性的竞态仍然存在。

## 2. P1：直接影响正确性、连续使用或安全判断

### P1-1：快速回复可能让输入框永久停留在“生成中”

证据：

- `src/renderer/src/stores/chatStore.ts` 的 `send()` 等 IPC 成功返回后才写入 `sending[sessionId] = true`。
- `src/main/ipc/message.ts` 在插入用户消息后立即 `void runReply(...)`，随后才把用户消息作为 IPC 结果返回。
- 主进程可能先推送 `streaming/done`；Renderer 收到 `done` 后先把 sending 设为 false，IPC 随后返回又将它覆盖为 true。

影响：

- 极快模型、Mock、缓存响应或本机错误路径可能让停止按钮永久显示。
- 用户只能切换会话或重启应用恢复。

建议：

- Renderer 在调用 IPC 前用 `clientRequestId` 乐观进入 `submitting`。
- 主进程返回结构化 `generationId`，之后所有 lifecycle 事件携带同一 ID。
- 仅当前 generation 的终态才能修改 session 状态；旧事件不得覆盖新任务。
- 状态由 `idle -> submitting -> streaming/waiting -> done/error/cancelled` 单向转换。

### P1-2：IPC 返回前可以重复发送，造成重复消息和任务互相取消

证据：

- `ChatInput.doSend()` 没有本地 `submitting` 锁。
- `canSend` 只依赖 `sending`，而 sending 要到 IPC 返回后才变为 true。
- 文档解析、数据库写入和标题生成均发生在 IPC 返回前。
- `beginGeneration()` 会取消同一 session 的上一 generation。

影响：连续按 Enter 可以插入两条相同用户消息；第二次 generation 以 `replaced` 取消第一次，留下不完整 assistant 消息。

建议：发送请求带不可重复的 `clientMessageId`，Renderer 立即锁定提交，主进程按该 ID 幂等插入；同一个 ID 的重试返回同一用户消息和 generation。

### P1-3：初始化失败和早退路径没有发送 assistant 终态

证据：`src/main/ipc/message.ts` 在项目任务、浏览器任务或 Skill 初始化失败时只发送临时 notice 后直接 `return`。这些 return 位于 `runModelReply()` 创建 assistant 消息之前。

影响：

- Renderer 已经把 sending 设为 true，却收不到 `done/error` 消息。
- 错误只显示五秒 toast，重进会话后看不到失败原因。

建议：所有回复路径先创建 generation/message shell，并在一个顶层 try/catch/finally 中写入持久终态；notice 只能作为提醒，不能替代消息终态。

### P1-4：取消、替换和进程中断的消息状态不准确

证据：

- 用户停止后，`runModelReply()` 把部分回答以 `done` 写入，仅额外显示“已停止生成”toast。
- `replaced/window_closed` 等非用户取消直接返回，可能保留数据库中的 `streaming`。
- `MessageStatus` 没有 `cancelled/interrupted/waiting`。
- 应用启动时没有把遗留 `streaming/pending` 消息恢复成 interrupted。

影响：历史中的半截回答看起来像完整结论；崩溃或快速重复发送后可能永久显示流式动画。

建议：增加 `cancelled` 和 `interrupted` 终态，并保存 `finishReason`。启动恢复时原子地把旧 pending/streaming 归档为 interrupted。部分回答必须在消息内永久显示“已中断”，而不是只靠 toast。

### P1-5：消息加载可以覆盖更新的流式状态

证据：

- `App.tsx` 切换 activeId 后异步调用 `chatStore.load()`。
- `load()` 成功后直接用数据库数组替换该 session 的内存数组。
- 同时到达的 `messageStreamed` 使用 `upsertMessage()` 更新内存；较晚完成的 load 可能用稍旧的数据库快照覆盖它。

影响：流式正文倒退、工具块短暂消失、done 状态重新变回 streaming。

建议：为 load 增加请求版本和数据库 revision；加载结果与内存按 message ID/revision 合并，不能整数组覆盖。流式消息使用单调 `revision`，旧 revision 丢弃。

### P1-6：切换会话会串附件和异步文件结果

证据：

- `ChatInput` 的 session 切换 effect 清理文本和菜单状态，但没有清理 `attachments`、`processingFiles`。
- 文件压缩/读取的 Promise 完成后直接向组件级附件数组追加，没有检查启动时的 sessionId。

影响：在会话 A 添加图片后切到 B，图片可能出现在 B；大文件在切换后完成解析，也会被追加到当前会话。这既是体验问题，也是潜在的数据误发问题。

建议：草稿和附件按 sessionId 存储；每个异步附件任务绑定 sessionId/abort controller，完成时只写回原 session。删除会话或退出登录时清理对应草稿和临时数据。

### P1-7：文档、工具证据和图片的跨轮上下文契约仍不完整

已确认问题：

- `buildHistory()` 先 `injectDocuments()`，随后 `replaceActiveUserRequest()` 覆盖最后用户消息，文档正文当轮可能丢失。
- 历史过滤只看正文或附件，纯 `toolContext` assistant 消息会被删除。
- `toChatMessage()` 只把历史中的用户图片发给视觉模型；浏览器截图通常是 assistant attachment，纯文字追问也不会获得像素。
- 文档解析结果只存在本次 `docTexts`，消息数据库只保存“已解析 N 字”，无法跨轮恢复正文。
- `fitHistoryToTokenBudget()` 逐条跳过超预算消息，可能留下没有对应问题的回答或没有对应调用的证据。

影响：用户第二问“继续分析”“图片里这个地方”“根据刚才文档”时，模型可能没有真实依据却继续回答。

建议：构建不可变 `TurnEnvelope`，把用户正文、文档引用、图片引用、结构化选择和工具证据一起持久化；按完整 turn/连续后缀裁剪，长期对话使用带来源的摘要。

### P1-8：能力路由产生互相矛盾的对话行为

当前行为：

- 普通非 Agent 对话只要提供方支持，就无条件先走联网搜索；用户没有可见搜索开关，`SendMessageInput.search` 也未实际参与路由。
- 有项目的会话，只要不命中“明显联网查询”，几乎都会进入 Coding Agent；“你好”“解释概念”等普通交流也可能被强制调用项目工具。
- 带图片时 `projectEligible = false`，项目、插件和浏览器工具链全部关闭；用户不能一边给截图一边让 Agent 检查项目或实时页面。
- Chrome 当前由关键词和最近消息推断；目标设计已经改为模型调用 `browser.activate`。
- 没有项目时显式插件不会获得插件工具，可能被静默清理成普通回答。

影响：同一句话因为是否选了项目、是否附图或提供方不同而走完全不同的系统，用户无法形成稳定预期。

建议：统一为模型驱动的 capability loop：第一轮只暴露小型能力入口，模型以 `tool_choice:auto` 选择项目、浏览器、联网或插件；宿主再动态展开最小工具集合。图片是输入模态，不应排斥工具能力。

### P1-9：多插件选择 UI 与真实执行不一致

证据：

- `ChatInput` 能识别并显示多个 `@plugin` 标签。
- `doSend()` 没有把 `selectedPlugins` 转成 `pluginIds` 传给 `chatStore.send()`。
- 后端 `resolvePluginSelection()` 的正文正则只解析第一个 mention。

影响：用户看到多个插件均已选择，实际上只有第一个进入任务快照，属于误导性确认。

建议：发送结构化 `explicitPluginIds`，正文 mention 只负责补全展示；主进程按结构化 ID 校验并把最终快照回显到时间线。未执行的插件不能显示成已使用。

### P1-10：Skill 自动匹配过宽，并被错误描述为用户显式激活

证据：

- `descriptionMatches()` 对中文描述使用任意连续双字匹配，多个常见词就可能触发 Skill，且没有评分或阈值。
- `skillPrompt()` 无论自动还是显式，均告诉模型“本轮已由用户明确激活”。
- `isMentioned()` 只要正文包含 `$name` 或 `@name` 子串就视为选择，缺少完整 token 边界。

影响：普通问题可能加载意外 Skill；审计、模型提示和用户时间线无法区分 automatic/explicit，模型会高估用户授权意图。

建议：显式结构化选择优先；自动匹配使用可解释评分、完整 token 和 `allowImplicit`；prompt、时间线和审计保存真实 trigger。自动匹配不能伪装成用户选择。

### P1-11：后台审批缺少会话归属，过期后不会自动消失

证据：

- `ApprovalDialog` 从所有 session 的请求中挑选过期时间最晚的一条，全局弹出，但不显示会话标题，也不自动切换到对应会话。
- 组件用 `Date.now()` 过滤过期项，但没有到期 timer；如果 store 不再变化，弹窗会一直停留。

影响：同时运行多个会话时，用户可能在不知道来源的情况下批准后台任务；过期弹窗点击后才提示失效。

建议：审批必须显示会话标题、项目和触发消息摘要，并提供“查看对话”；到期自动关闭。后台会话先显示非阻塞 badge/通知，高风险审批只有在用户明确查看来源后才能确认。

### P1-12：本地 JSON 持久化会随长对话和截图快速退化

证据：

- 已登录模式固定使用 account-scoped `MemoryStore`，即单个 `ai-agent-data.json`。
- 每次 `persist()` 都同步 `JSON.stringify` 全部 sessions/messages，再重写整个文件。
- 流式 assistant 消息约每 200ms upsert；图片以 Base64 放在 message attachment 中。

影响：对话和截图增多后，主进程频繁复制、序列化和写入整库，造成输入延迟、流式卡顿、磁盘放大和损坏风险。图片仍以明文 Base64 存放在本地 JSON 中。

建议：迁移到 account-scoped SQLite/增量存储；消息正文增量更新，图片使用独立 artifact 文件和数据库引用；增加配额、级联删除、孤儿回收和可选本地加密。

## 3. P2：明显影响体验、可理解性或规模

### P2-1：Agent 的模型输出实际不是连续流式

`runToolCallingLoop()` 只要提供了 `requestUserInput` 回调，就在每一轮缓冲全部模型事件，等整轮完成并确认没有提问后才一次性转发。项目/浏览器 Agent 总是传该回调，因此正文和思考常以突发方式出现，而不是实时显示。

建议将“是否调用 request_user_input”从流事件缓冲中解耦：工具调用 delta 与正文分通道；只抑制同一轮中明确属于提问卡片的重复正文。

### P2-2：启动总是偏向空白会话，而不是恢复工作现场

`sessionStore.init()` 会寻找任意无标题空会话，找不到就新建；不会恢复上次活跃会话。空白会话复用也没有按项目路径隔离，主进程可能返回另一个项目留下的空会话。

建议持久化 `lastActiveSessionId`；启动优先恢复，用户点击“新对话”时再复用同项目空白草稿。

### P2-3：文本草稿会在切换会话时丢失

sessionId 变化时 `setValue('')`，没有 per-session draft。用户切出去查看资料再返回，未发送内容丢失；附件却可能反向串过来，状态策略不一致。

建议为每个 session 持久化短期草稿：正文、附件引用、显式 Skill/插件选择和页面预选统一保存；成功发送后清空该 session 草稿。

### P2-4：会话切换不会重置消息跟随状态

`MessageList` 不接收 sessionId，组件在会话切换时复用。若用户在 A 向上滚动，`stickRef=false` 会带到 B，B 可能不滚到最新消息并立即显示“新内容”。

建议按 session 保存滚动位置，首次打开默认到底部；切换时取消旧 animation frame 和 observer 状态。

### P2-5：消息加载没有 loading/error/分页

切换会话时，在数据返回前直接显示空状态；失败只留在 store 中且界面不展示。数据库和 Renderer 一次加载、排序并渲染整个会话，没有游标分页或虚拟列表。

建议增加 skeleton、内联重试、按时间游标向上加载和消息虚拟化。图片与代码块应懒加载。

### P2-6：失败和降级反馈依赖临时 toast

搜索失败转普通回答、停止生成、初始化失败和模型错误大量使用 4～5 秒 toast。重进会话后无法知道发生过降级；部分回答也没有永久错误标识。

建议把影响答案可信度的事件写进消息状态区：是否联网成功、使用了哪些能力、是否回退、是否截断、是否中断。toast 只提示，不承担审计。

### P2-7：未配置模型时静默进入 Mock，容易造成信任误解

主进程缺少有效 preset/API key 时直接 `scheduleMockReply()`。空状态虽提到“本地演示”，但消息本身没有持续标识，用户可能把演示结果当真实模型结果。

建议未配置时进入明确 Demo 模式：输入区和每条演示回答均显示标识；生产默认可以直接阻止发送并引导配置。

### P2-8：历史消息缺少模型与能力来源

消息没有持久化 model preset、provider、reasoning effort、联网状态、active skills/plugins 或 finish reason 的统一 metadata。切换模型后，历史回答看起来都来自当前模型。

建议生成开始时固化 `GenerationSnapshot`，消息头可查看模型、时间、能力、项目和完成原因；默认 UI 保持简洁，详情可展开。

### P2-9：后台补充提问缺少可见提醒

`request_user_input` 只在对应 session 的输入区上方显示。用户切到其他会话后，任务会一直等待，侧栏没有 badge、标题状态或系统通知。

建议会话列表显示“等待回答/等待批准/生成中/失败”状态；点击 badge 回到相应卡片。等待应有超时和取消入口。

### P2-10：附件处理顺序和类型信息可能不稳定

- 多文件使用 `Promise.all`，按完成顺序 append，展示/发送顺序可能与用户选择顺序不同。
- WebP/GIF 等图片转成 JPEG data URL 后仍保留原 `contentType`。
- 图片没有在 Renderer 侧统一执行字节上限检查；超限要到 IPC 校验后才失败。
- 主进程文档解析期间没有独立进度，用户只看到发送按钮仍可用。

建议预分配附件槽位保持顺序；编码后使用真实 MIME/尺寸；在 Renderer 和主进程共享同一限制常量；解析作为 submitting 子状态展示。

### P2-11：顶部会话标签的关闭按钮实际是“新建对话”

`ChatPanel` 当前标签旁的 X 调用 `create()`，既不关闭也不删除当前会话。图标语义和实际操作不一致。

建议要么移除 X，要么改为“关闭标签并返回最近会话”；新建只使用 Plus。

### P2-12：系统提示强制所有语言使用简体中文

`AGENT_SYSTEM_PROMPT` 要求“使用简体中文”，因此英文用户、翻译场景或用户明确要求其他语言时也可能被强制中文。

建议改为“默认跟随用户最近一条消息的语言；用户明确指定时服从指定语言”。

### P2-13：图片预览的键盘和焦点行为不完整

图片预览有 dialog 角色和缩放，但没有 Escape、焦点陷阱、打开后聚焦、关闭后焦点恢复；缩放只用按钮，缺少滚轮/快捷键和适应宽度。

建议补齐键盘交互、焦点管理、100%/适应窗口切换，并持久化每个图片块的折叠状态仅限当前 UI 会话。

### P2-14：缺少编辑、重试和从此处分支

模型请求失败或用户想修正问题时，只能重新复制发送；没有“重试同一 generation”“编辑并重发”“从此处创建分支”。长对话中这会产生重复消息并污染上下文。

建议先实现幂等重试，再增加编辑重发；编辑历史消息应创建分支或明确截断其后的消息，不能原地篡改已经产生的回答。

### P2-15：搜索只匹配会话标题

侧栏搜索不搜索消息正文、文件名、工具证据或项目。标题又只是第一行前 30 个字符，长时间使用后很难找到旧结论。

建议提供本地全文索引，结果显示会话、命中片段和时间；敏感/已删除 artifact 不进入索引。

## 4. 需要分别优化的对话场景

### 普通问答

当前问题：默认先尝试联网；项目会话里可能被强制转成 Agent。

目标：模型在一个统一 `tool_choice:auto` 循环中决定是否需要外部能力；纯知识问答直接回答，不启动搜索、项目或 Chrome。

### 联网问答

当前问题：联网由 provider 和宿主路由决定，用户不可见；失败后静默清空内容并回退。

目标：把 web search 做成模型可选能力，时间线显示“搜索中/已完成/失败回退”；答案永久保存来源和是否成功联网。

### 项目问答与 Coding

当前问题：只要会话关联项目，多数非搜索请求都会进入 Coding Agent并强制首轮工具，普通闲聊也受影响。

目标：始终让模型看到轻量项目能力入口；只有需要实时项目事实或修改时才激活项目工具。读取、修改、运行和提交仍分别受权限约束。

### 图片 + 项目/浏览器

当前问题：附图会关闭全部项目和浏览器工具。

目标：视觉输入与工具调用可组合；模型既能看用户图片，也能读取项目文件或调用浏览器截图进行对比。图片引用必须结构化、按需跨轮携带。

### 文档问答

当前问题：解析正文当轮可能被覆盖，也不持久化；第二问只知道文件名和字数。

目标：文档正文保存为受限 artifact，消息保存 documentRef；上下文按段落检索，不反复塞入完整文档。解析失败应允许重新解析或下载诊断。

### Skill 对话

当前问题：自动匹配可能过宽，并被描述为用户显式激活；非项目 Skill 只有提问工具循环，其他声明工具未必可执行。

目标：显式与自动来源分开；Skill 只提供工作流和能力需求，由统一 capability loop 解析可用工具，不因是否绑定项目而切换成另一套循环。

### 插件对话

当前问题：多个标签只执行第一个；无项目可能完全不执行；插件是否只是发现还是已经调用不清楚。

目标：结构化选择插件，任务开始时固化快照；时间线区分 discovered/selected/tool-called/failed。无 workspace 依赖的插件可在普通对话使用。

### Chrome 对话

当前问题：仍由关键词路由，selected 页面不可靠，连续调用和证据边界未完全闭环。

目标：按新的模型驱动 Chrome MCP 设计实施 `browser.activate -> 可信页面绑定 -> 动态工具目录 -> 官方 MCP 调用 -> 证据持久化 -> finally 释放`。

### 长对话

当前问题：消息全量加载；token 裁剪可能断裂；整库 JSON 持久化随图片增长。

目标：分页和虚拟化、完整 turn 裁剪、来源化摘要、独立 artifact、增量数据库以及会话容量提示。

### 多会话后台任务

当前问题：可以并行发送，但审批、补充问题、滚动和草稿缺少会话级隔离与状态提示。

目标：每个 session 有独立 generation/draft/scroll/waiting 状态；侧栏可见，审批显示来源，切换不会串数据。

### 失败、取消和恢复

当前问题：部分结果可能标成 done，错误主要依赖 toast，重启遗留 streaming。

目标：持久化 finishReason，明确 cancelled/interrupted/error；启动恢复旧任务；提供安全的幂等重试。

## 5. 推荐目标架构

### 5.1 Generation 事务

每次发送生成：

```text
clientMessageId
  -> 原子插入用户消息
  -> generationId + generation snapshot
  -> submitting
  -> streaming | waiting-input | waiting-approval
  -> done | error | cancelled | interrupted
```

所有 IPC、流式事件、工具事件和附件 artifact 都携带 generationId 与单调 revision。Renderer 只接受当前 generation 的更新。

### 5.2 统一能力循环

普通问答、项目、浏览器、联网、Skill 和插件不再各自决定一套执行入口：

1. 第一轮暴露小型 capability tools。
2. 模型自行选择是否激活。
3. 宿主校验结构化选择、权限与环境。
4. 下一轮动态展开最小工具集。
5. 工具结果进入统一证据和时间线。

用户文字可以帮助模型判断，但宿主不再以正文正则作为安全或连接决策。

### 5.3 TurnEnvelope 与上下文编译器

每一轮持久化：

- 用户正文；
- 文档/图片 artifact refs；
- 显式 Skill/插件/页面选择；
- generation snapshot；
- tool calls、结构化证据和 finish reason；
- 可见时间线块。

发送给模型时由上下文编译器按模型能力和预算选择内容，不修改数据库中的原始 turn，也不把旧证据冒充实时状态。

### 5.4 会话级 UI 状态

Renderer store 按 session 保存：

- draft；
- attachment processing；
- generation lifecycle；
- pending input/approval；
- scroll position；
- unread/new-content；
- load revision/error。

切换会话只切换视图，不销毁或串用这些状态。

### 5.5 增量持久化与 Artifact Store

- SQLite 保存 sessions/messages/generations/blocks/refs。
- 图片和大文档独立文件保存，数据库记录 hash、MIME、大小、来源和生命周期。
- 流式文本按节流增量更新单条消息，不重写整库。
- 会话删除、账号退出和配额清理级联回收 artifact。

## 6. 实施优先级

### 第一批：发送与终态可靠性

1. clientMessageId/generationId/revision。
2. optimistic submitting 与重复发送锁。
3. 所有早退进入持久 error 终态。
4. cancelled/interrupted 状态和启动恢复。
5. load/upsert revision 合并。
6. 增加 `chatStore`、message IPC 和完整发送链路集成测试。

### 第二批：跨轮上下文与会话隔离

1. 修复文档注入覆盖和纯 toolContext 过滤。
2. TurnEnvelope 与 artifact refs。
3. per-session draft/attachments/scroll。
4. 历史图片策略、完整 turn 裁剪和长期摘要。

### 第三批：模型驱动能力路由

1. 统一可选工具循环，取消普通聊天默认联网。
2. 项目、联网、插件和 Chrome 使用小型 capability activation。
3. 图片输入与工具能力组合。
4. 显式/自动 Skill、插件来源结构化。
5. 逐轮动态工具目录。

### 第四批：审批、持久化和规模

1. 审批来源、过期 timer 和后台状态 badge。
2. SQLite + Artifact Store。
3. 消息分页、虚拟化、全文搜索。
4. 图片/文档配额、清理和隐私设置。

### 第五批：交互完善

1. 持久错误/降级/能力来源展示。
2. 重试、编辑重发和对话分支。
3. 模型来源与 finish reason 详情。
4. 图片预览无障碍和快捷操作。
5. 多语言跟随用户。

## 7. 必须补充的测试

- IPC 返回晚于 `done` 事件时 sending 仍回到 idle。
- 100ms 内连续两次提交只插入一个 clientMessageId。
- 项目/Skill/插件/browser 初始化每一个失败分支都生成 error 消息。
- user cancel、replaced、window close、app crash 的终态与恢复。
- load 与 stream/upsert 交错时 revision 单调，不丢块、不倒退。
- 会话 A 解析附件时切到 B，结果只进入 A。
- 多插件结构化选择与任务快照一致。
- 自动 Skill 不能显示成 explicit，低相关中文双字不触发。
- 普通问答零 search/零 MCP/零 workspace 工具；模型明确选择后才展开。
- 图片 + 项目工具、图片 + Chrome、图片 + 插件组合。
- 文档第一问、第二问、重启后追问均能引用同一 artifact。
- 审批来自后台会话时显示来源，到期自动关闭。
- 10,000 条消息和多张截图的分页、启动、流式写入与删除性能。

## 8. 当前测试覆盖缺口

仓库有较完整的组件、TaskRuntime、工具和安全测试，但关键编排层仍缺：

- 没有 `chatStore` 的发送生命周期测试。
- 没有覆盖 `src/main/ipc/message.ts` 完整 send → runReply → terminal 的集成测试。
- Session 测试把“启动选择任意空白会话”固化成预期，尚未覆盖恢复上次现场。
- ApprovalDialog 测试覆盖按钮 scope，但没有覆盖自动过期、后台会话来源和多审批排队。
- ChatInput 测试没有覆盖重复提交、会话切换中的异步附件和 per-session draft。
- 历史测试覆盖局部转换，但没有覆盖真实 `buildHistory()` 的文档注入顺序和完整 turn 裁剪。
- 没有崩溃后遗留 streaming 消息的恢复测试。

## 9. 完成标准

只有同时满足以下条件，才能认为对话系统进入稳定状态：

1. 每次发送都有唯一 generation，任何路径都有持久终态。
2. 会话切换、快速发送、停止、删除和重启不丢消息、不串附件、不留下假 streaming。
3. 模型而不是正文正则决定是否使用联网、项目、插件或 Chrome；宿主始终掌握权限。
4. 文档、图片和工具证据能按来源跨轮恢复，旧证据不会伪装成实时状态。
5. 用户能知道回答使用了哪个模型、哪些能力、是否联网、是否失败或降级。
6. 长对话使用分页、增量持久化和独立 artifact，不随 Base64 数据量线性拖慢整个应用。
7. P1 场景均有自动化集成测试，真实模型、真实 Chrome 和应用重启人工验收通过。
