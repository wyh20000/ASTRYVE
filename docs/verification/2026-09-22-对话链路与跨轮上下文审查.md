# 对话链路与跨轮上下文审查

> 日期：2026-09-22
> 范围：Renderer 输入与会话状态、消息 IPC、任务路由、附件处理、历史组装、模型工具循环、持久化
> 方式：静态代码审查及定向测试；未读取用户生产会话日志，未用真实模型重放特定会话
> 状态：问题清单，本文不代表缺陷已修复

## 结论

同一个会话的第二问确实可能缺少第一问的关键上下文。主要原因不是数据库完全不保存消息，而是持久化
内容与下一轮模型消息的转换不一致：文档正文没有持久化且当轮注入会被覆盖，只有工具块的消息被历史
过滤，纯文字追问不会重发先前图片，超预算历史也没有连续性保证。输入区和任务路由另有几处会让用户
误以为能力已启用或会话已恢复，但实际上没有。

## 已确认的问题

### P1-1：文档正文在当轮被覆盖，跨轮又无法恢复

- 复现：上传 PDF/Word/表格并问其中的内容；再在同一会话追问文档细节。
- 证据：`src/main/ipc/message.ts` 的 `prepareAttachments` 将文件 `dataRef` 清空，仅把提取正文放进
  临时 `docTexts`（约 154-189 行）。`buildHistory` 先调用 `injectDocuments`，紧接着调用
  `replaceActiveUserRequest`（约 369-394 行），后者会覆盖最后一条用户字符串消息。`runReply` 总是将
  `modelUserRequest` 传入该参数（约 328-348 行）。
- 影响：当轮模型可能根本收不到文档正文；下一轮数据库只有文件名和解析元数据，无法恢复原文。
- 建议：先完成当前请求改写，再把文档作为独立、带来源与长度限制的内容附加；安全持久化提取文本或
  内容引用，跨轮按需恢复。测试必须覆盖普通请求、`/skill`、`@plugin`、图片与文件混合及第二轮追问。

### P1-2：仅有工具块的消息在跨轮历史中被丢弃

- 复现：浏览器 `inspect` 成功后任务失败，助手没有最终正文；随后问“这个 Bug 是什么原因”。
- 证据：`src/main/ipc/message.ts` 约 607-620 行把 `browser.inspect` 的清洗结果放在
  `toolContext` 块；任务失败且无正文时只往时间线追加失败说明（约 668-679 行）。`buildHistory` 约
  382-385 行却只保留正文非空或带附件的消息，尚未检查块。
- 影响：界面可显示工具时间线，但下一轮模型看不到已经读过的页面证据。
- 建议：历史过滤以“有可回放内容”为准，包含有界 `toolContext`；将失败任务的未完成推测与经过验证
  的工具证据分开。补集成测试，不能只直接测试 `toChatMessage`。

### P1-3：图片第一问后的纯文字追问没有像素上下文

- 复现：第一问发截图，第二问只写“这里的错误怎么修”。
- 证据：`src/main/ipc/message.ts` 约 208 行仅根据本轮附件设置 `vision`；
  `src/main/services/history.ts` 约 9-33 行只在 `vision=true` 时将历史用户图片转为 `image_url`。
- 影响：第二轮仅见文字和可能的助手解释，无法重新检查图片；第一问只有图片无文字时，还会产生空的
  历史用户内容。不能让模型声称它重新看过截图。
- 建议：视觉模型按明确的跨轮图片引用策略保留最近相关图片；文本模型显式提示缺少像素并要求重新
  附图。限制数量和字节，避免重发整段历史全部图片。

### P1-4：初始化失败后输入框可能永久处于生成中

- 复现：显式插件不可用、Skill 解析失败或项目/浏览器任务创建失败后再次发送。
- 证据：`src/main/ipc/message.ts` 约 123 行异步启动 `runReply`；其约 224 行的插件解析可抛错，
  约 285-323 行的错误路径仅发临时 `messageNotice` 并返回。`src/renderer/src/stores/chatStore.ts`
  约 63-84 行先将 `sending` 设为 `true`，只有收到状态为 `done/error` 的助手消息才清除。
- 影响：消息已经入库，用户看过瞬时提示后仍不能在原会话继续发送。
- 建议：所有终止路径都发送带请求 ID 的终态事件或持久化错误消息；前端处理失败和取消，并对异步
  回调加兜底。测试应覆盖解析异常、任务创建失败、取消和窗口切换。

## 交互与调用时机

### P2-1：无项目时显式插件可能被静默忽略

`src/main/ipc/message.ts` 约 224-226 行解析并删除 `@plugin`，但无项目且未触发浏览器任务时走
约 309-324 行的普通 Skill 分支，并未创建插件工具任务。当前 `ChatInput.tsx` 约 227-242 行也未
提交结构化 `pluginIds`。用户以为指定了插件，模型却只能普通回答。应让选中的插件进入受限任务，
或在发送前明确告知当前会话不能使用，不能静默降级。

### P2-2：普通聊天无条件先尝试联网

`src/main/ipc/message.ts` 约 325 行把所有非图片、非任务请求设置为 `useSearch`，未根据用户意图或
输入的 `search` 字段判断；约 689-693 行实际进入搜索，失败后约 717-734 行回退普通聊天。
简单闲聊和基于现有历史的追问也会增加联网延迟或产生无关搜索。应由用户开关或明确的信息需求控制，
并在 UI 中区分“可联网”与“本轮确实联网”。

### P2-3：浏览器续接和工具可见性由宽泛正文规则决定

`src/main/ipc/message.ts` 约 227-230 行以关键词及最近消息推断浏览器任务；
`src/main/services/browser/browserConversation.ts` 约 31-45 行将普通 `image` 块和含页面词的计划块也
视作浏览器上下文。谈论一张图片或一个页面 Bug 的追问可能意外启动 Chrome；短追问又可能漏判。
这与已提交的“显式 Chrome 上下文”设计相对应，实施前应保持浏览器能力与其他插件 MCP 的权限边界。

### P2-4：长对话裁剪可能保留断裂的问答

`src/main/services/history.ts` 约 69-90 行从新到旧逐条选择，某条消息超预算时继续检查更旧消息，
可能留下回答而丢掉对应问题。当前消息过长时保留的是文本开头，并且没有摘要或用户可见的截断提示。
应按完整问答或连续后缀裁剪，保护当前问题和工具证据；超预算时显式告知，长期对话提供有来源的摘要。

### P2-5：会话草稿与异步消息加载存在竞态

`src/renderer/src/components/chat/ChatInput.tsx` 约 121-128 行切换会话清空草稿；约 227-242 行旧
会话发送完成后又无条件清空当前组件输入，可能删除切换后新会话的草稿。
`src/renderer/src/stores/chatStore.ts` 约 56-60 行的异步 `load` 直接覆盖已收到的流式消息列表，
旧快照可能暂时抹掉新消息。草稿应按 `sessionId` 隔离；加载结果应按消息 ID 合并并防止过期响应覆盖。

### P2-6：启动默认进入空会话而非上次活跃会话

`src/renderer/src/stores/sessionStore.ts` 约 24-41 行优先复用空白会话，否则新建。旧会话仍保存在
侧栏，并非数据丢失，但用户重启后直接追问可能落入新会话，主观感受像“第二问没有第一问上下文”。
建议恢复上次活跃会话；若产品坚持新会话优先，需显著提示当前会话身份。
